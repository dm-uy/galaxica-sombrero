# Bounded development-flow consumer

Run `python3 tests/flow_contract_probe.py --root . --cases examples/flow-contract/cases.json` from the repository root. The command reads the actual live anchored norm bodies, prints one JSON report to stdout and LDD decisions to stderr. Exit 0 means all independently authored finite cases match; exit 1 means a contract refusal or discrepancy; exit 2 means unreadable or malformed case input.

The selected interpretation supports the ordinary success transitions (PHASE-303/405/503/603/604/901), activation and visual predicates (PHASE-201/403), changed-candidate renewal and its negation (PHASE-605; STATE-501/503), optional extension and E2E boundaries (PHASE-801/802/804), Debug default/unit/timing/failed spend/grants (STATE-301 through STATE-305), distinct retries and replay investigation (STATE-401/404), recovery and terminal guards (STATE-601/602/701), source repair during Finalize (FINAL-401), and common/conditional role fields and scans (RETURN-101/102/104/201/301/401/501/502/601/603/604/701/801). Controlled sentences are ordinary English clauses; this example does not introduce a required authoring format. Missing or unsupported critical clauses refuse evaluation rather than supplying defaults. Numeric grant bounds come from the unchanged GATE-1209.

`cases.json` contains generic initial facts, finite events, actual return-shaped data, optional adapter cap/grant data and independent expected outcomes. The finite examples support nonempty text identities and diagnostic fields; other interface shapes require declared adaptation. Evidence paths and hashes resolve against the supplied root. The unchanged FORMAT document supplies generic artifact bytes for the example; it does not certify a plan, test run or real role judgment. The return validator checks populated supported types for each phase/status, required artifacts, identities, evidence containment/hashes and scan identities. QA retains its test summary, all eight scans, findings and limitations for SUCCESS, BUG_REPORT and BLOCKED; a non-success scan can be FAIL or BLOCKED. Debug FIXED reaches renewed QA without another entry charge and invalidates earlier judgment. Initial spend must be a nonnegative integer and cannot be boolean. Unknown fields require a declared extension with type, meaning, producer, consumer, required conditions and version.

Owner grants require supplied external authority, matching scope/input/candidate, bounded additional entries and cost plus readable hashed evidence. This example assumes the caller's external authority premise has already been authenticated. It cannot authenticate a human decision from a model return, file path or hash. Initial QA/Review evidence premises are likewise supplied facts for finite cases; independent release review establishes real approval and judgment outside this consumer.

The consumer launches no agents, changes no repository, persists no workflow, reconstructs no approval and demonstrates no provider or product adoption. It interprets a selected subset of delivered prose. Full source accounting, compound obligations and all semantic meaning require independent review. The public tests mutate actual delivered clauses in isolated copies, retain before/after/restored identities, check specific refusals and run the real CLI before and after restoration. Separate return-data controls refuse missing BUG_REPORT fields before phase or counter advancement.

Before each phase action, a finite `activate` event or supplied `activationEvidence` must contain a current receipt: phase, role, run/input/candidate identities, `rolePath`, `protocolPaths` and hashed `readEvidence`. The caller supplies authenticated `assigned_role_paths` and `assigned_protocol_paths`; readable hashes check those declared assignments and bytes, and cannot establish whether a human or live worker actually read them. The initial success case supplies explicit events for each phase; removing them refuses before the first return. Other initial cases declare their receipts as external facts.

The canonical visual encoding uses integer `componentNodes`, boolean `testsOnly`, and integer `scannedNodes` for PASS. At least three new or modified nodes activate the mechanical gate unless the work is tests-only; PASS must show at least one scanned node. The selected output encoding is a line `scannedNodes=N` matching the declared count, alongside command, integer zero exit and real evidence. Adapters can declare another encoding preserving the same observations. A nonapplicable result supplies actual activation facts and reason.

Code SUCCESS supplies a `doxygen` record matching the caller's explicit boolean `doxygen_required`. A nonapplicable record has reason and actual applicability/prohibition evidence. An applicable record has real command/exit/output, current input/candidate identities, hashed evidence, a hashed `mapPath` and nonempty hashed per-file XML `fileChecks`. The caller's authenticated `doxygen_final_check_verified` premise records final-Code ordering; the bounded consumer cannot infer that order or real acceptance from a hash. A regression builds actual XML in an isolated copy, checks those bytes and rejects missing, failed, stale or waived records. The canonical documentation-only cases use a reasoned nonapplicable record; their FORMAT artifact certifies no real role verdict or Doxygen build.
