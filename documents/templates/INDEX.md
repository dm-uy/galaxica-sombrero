# Project template index

<!-- anchor: documents.templates.index.forms -->

## Five current forms

The default forms are [AGENTS](AGENTS.md), [VISION](VISION.md), [ROADMAP](ROADMAP.md), [TASKS](TASKS.md) and [HANDOFF](HANDOFF.md). Actual project records follow declared local metadata, not the neutral card format. Experience/results and decisions are durable event-driven records without extra mandatory templates. Existing required registers remain binding; development-specific specifications belong to their separately owned protocols.

- `AGENTS.md`: entry/profile and document map.
- `VISION.md`: goal/readiness.
- `ROADMAP.md`: outcome route.
- `TASKS.md`: authorized work and finish.
- `HANDOFF.md`: present baton.

## Choosing and checking the forms

Each of the five files retains a complete pasteable drafting form and a separately fenced complete fictional filled record for Meadow document review. Placeholders belong to the drafting form only. Filled records include full source, grant, result and retained-history bodies in the five imagined files; their path/section references navigate that fictional project and are not real repository evidence. There is no sixth primary form.

Use the declared local profile before choosing metadata, layer paths, status labels or budgets. A new project needs actual new purpose/intake evidence. An existing project with missing PM files needs reconstruction from its real records. A conventions migration needs matching scope, old/new owning homes and preserved history. Resume needs current work/artifact verification and prior-approval lookup, not a fresh bootstrap. Project records follow their own adopted metadata; the neutral card here describes the template carrier only.

The owning operations are [conventions](../conventions.md), [lifecycle](../../process/lifecycle.md), [batch](../../process/batch.md) and [session](../../process/session.md). Forms carry their resulting fields rather than replacing those operations. Existing auxiliary records keep their roles; no mandatory decision, specification, reconstruction, question or runtime-specific extra template is introduced.

| Filled record | Positive case | Boundary conclusion |
|---|---|---|
| AGENTS | declared single layer, ownership/events, new/existing/migration/resume | missing file is not greenfield; profile text never grants adoption |
| VISION | observable qualified result, source snapshot distinct from idea pool | incomplete input and unmeasured reader effect do not prove readiness |
| ROADMAP | P1 done, P2 current, changed T-203 dependency, matching diagram, retained P4 | restore erased failure; status is read-only; text/diagram drift blocks closure |
| TASKS | matching B-002 grant, independent method, full packets/results, blocked/held carryover | fake consent refuses execution; S2 blocks T-203; unknown effect investigated before retry |
| HANDOFF | cold-session recovery, prior approval, checked revision, owner-first queue/traps | foreign ignored resources preserved; expired trap moves to dated history |

Review complete content, not merely labels or valid fence syntax. An actual project reader must be able to identify the next authorized action, its input and output, remaining evidence and reserved decision. Software specialization remains conditional on the project's chosen execution method and unchanged software gates. New observations are recorded; no learning or improvement-measurement program is activated by these forms.
