# Phases

The flow defines functional boundaries. A harness binds these boundaries to its own nodes through {{cap:workflow-orchestration}}; node names and packaging do not change the obligations. The orchestrator consumes the validated returns in [role returns](../protocols/role-returns.md) and maintains [run state](run-state.md).

<!-- anchor: flow.phases.entry -->

## Entry

Select this software cycle for a new feature or a substantial bug fix. Substantiality follows behavioral consequences and uncertainty, not line count. Architect → Code → independent QA belongs to that development slice. Documentation-only work and small local corrections stay outside this cycle: inspect the affected result and use only directly relevant checks; do not create a flow run, specification, independent QA/Review/Finalize assignment or evidence archive just to process them. A documentation edit does not become feature work merely because it lives in a code repository.

A substantial implementation change still receives its required QA even when its slice also contains documentation. Preserve existing frozen-run evidence and report its original scope honestly; a later document-only correction is a separate lightweight update, not a reason to relabel an old verdict or restart QA over unchanged implementation.

- **PHASE-101** MUST: Begin only from an explicitly authorized flow invocation and approved specification or approved batch scope under [the gate contract](../process/gates.md). Resolve the actual task, target, framework and specification identities before dispatch; an approval for another scope is insufficient.
- **PHASE-102** MUST: Acquire and record the actual repository baseline before any mutating phase. Verify the repository and its current branch, HEAD and dirty/untracked state; a stated baseline or a worker report is not acquisition. Preserve existing changes and isolate work when necessary within authorization.
- **PHASE-103** MUST: Discover the available runtime operations through {{cap:capability-discovery}} and establish role permissions, isolation, persistence, verification commands, autonomy and resource limits before starting. Refuse an unavailable required mechanism unless its declared fallback preserves the obligation.
- **PHASE-104** MUST: Classify the task from actual project and requirement evidence as GREENFIELD or BROWNFIELD. Keep project type, task type and UI applicability explicit; an empty directory alone does not authorize product bootstrap, environments, launchers or dependencies.
- **PHASE-105** MUST: In authorized autonomous work, resolve routine choices and collapse alternatives on the specification criteria without inventing an extra plan gate. Missing owner authority, contradictory requirements or a human-dependent deficiency stop the affected action; existing approval remains valid for its recorded scope.

- **PHASE-106** MUST: Echo the resolved task/target/framework and actual plan-location rule at entry and verify the target is reachable within the active session write roots. Validate the configured entry role/model and actual launch environment before starting; a silent fallback to a different role or wrong topology is ERROR, not an equivalent invocation. Keep the launcher responsible for environment/isolation and orchestration responsible for sequencing, without duplicating design policy.

## Activation and ownership

- **PHASE-201** MUST: Before any phase action, load the assigned role and its applicable protocols through {{cap:skill-loading}} and project rules through {{cap:rules-injection}}. Record the actual read evidence; absent assigned protocol/read evidence refuses phase action as CRITICAL_RULE_VIOLATION.
- **PHASE-202** MUST NOT: Adopt a role merely because a role table or protocol was read. Only the explicitly assigned actor acts within that phase; reading an activation table confers neither an invocation nor write authority.
- **PHASE-203** MUST: Keep producer and consumer ownership aligned: Bootstrap is produced by scoped reconnaissance, Architect by the architect, Code by the coder, QA by an independent QA judge, Review by an independent reviewer, Debug by the debugger, and Finalize by the explicitly assigned finalization actor following [Finalization](finalize.md). The root or architect may carry that function; an adapter declares any split finalizer role under ROLE-704, preserving its permissions, inputs, checks and returns. The root orchestrator owns dispatch, return acceptance, counters and transitions; a role never promotes itself to root.
- **PHASE-204** MUST: Read the actual approved specification, plan where available, scope, artifacts and current failure evidence required by the assignment before acting. Activate each extension with its own declared role/protocol as well as the shared boundary protocol; memory of a protocol is insufficient.

<!-- anchor: flow.phases.bootstrap -->

## Bootstrap and reconnaissance

- **PHASE-301** MUST: Bootstrap performs a bounded read-only project inventory before design. Read applicable project instructions and existing durable documents, inspect the configured code map before code navigation, and identify actual source shape, useful files, entry points, structure, relevant requirements, commands, constraints and missing inputs. Use scoped search/reconnaissance rather than unrestricted repeated full-tree reads.
- **PHASE-302** MUST: Bootstrap returns its actual map and evidence path, file count, empty-tree fact, classification hint, recommendations and limitations. The hint guides Architect and does not decide approval or scope. If applicable onboarding or reconnaissance is needed, retain its required inputs and evidence interface to [bootstrap](../process/bootstrap.md) and [reconnaissance](../process/reconnaissance.md).
- **PHASE-303** MUST: On a validated Bootstrap SUCCESS, proceed to Architect. An embedded Bootstrap is permitted only when the adapter declares its producer, consumer and equivalent read-only boundary evidence before Architect acts; unavailable required inventory produces BLOCKED rather than an invented map.

## Architect

- **PHASE-401** MUST: Architect reads the full approved specification and relevant manifests, requirements and mapped sources. For ambiguous design, hold two or three plausible alternatives before selecting one on explicit scope, utility, compatibility and acceptance criteria; record the rejected alternatives and the collapse reason. In explicitly interactive work, Architect asks the necessary clarifying questions and presents two or three hypotheses for the owner to select the collapse; it presents the bird's-eye diagram for owner approval and surfaces specification contradictions instead of resolving them best-effort. The proposal, owner selection and diagram decision are current phase evidence. Detailed interactive procedure remains at [Architect](../roles/architect.md) and [autonomy](../policies/autonomy.md); these conditional owner steps do not add gates to approved autonomous work governed by PHASE-105.
- **PHASE-402** MUST: Produce the actual development plan at the dictated project path, not a similarly named default. Record classification, independently implementable slices with tests, affected components/data flow, MAY EDIT and DO NOT TOUCH, task constraints, cardinal project rules, measurable acceptance thresholds, delivery sinks, external identifier evidence, deviations, deficiencies and exact project commands. Preserve the interfaces to [development plans](../protocols/dev-plan.md), [graphs](../protocols/graph.md) and the applicable [brownfield](../protocols/spec-brownfield.md) or [greenfield](../protocols/spec-greenfield.md) specification protocol; their detailed templates remain at those homes. The plan preserves four mandatory architectural pattern interfaces on their applicable surfaces: Layer Isolation identifies layer responsibilities and dependency boundaries; Plugin API + Direct Integration identifies the plugin contract and direct integration data flow; Backend Tests + LDD identifies backend acceptance tests and the required execution trajectory; Headless UI Testing identifies applicable UI behavior and its headless observable tests. Architect derives these outputs from the specification and classification, records each pattern's applicability and delivers them to Code and independent QA. Detailed design treatment remains at [development plans](../protocols/dev-plan.md) and [Architect](../roles/architect.md), with backend tests/logging detail at [tests](../code/tests.md) and [LDD](../code/ldd.md), and UI testing detail at [UI](../code/ax-ui.md). A later-home label does not waive these current outputs.
- **PHASE-403** MUST: Check the visual gate using its actual activation criteria. An applicable visual PASS requires the real command, output, exit code and evidence artifact; a NOT_APPLICABLE or SKIPPED result requires the actual activation facts and a reason. A missing output, fabricated success or unsupported waiver blocks Code; review diagram/data-flow consistency even when no mechanical visual check applies. The mechanical visual gate activates when at least three new or modified component nodes are present, except for tests-only work. An applicable PASS output must demonstrate at least one scanned node. The consumer checks these actual counts and the exception before accepting PASS or SKIPPED; an empty scan cannot establish visual PASS. Detailed diagrams remain at [development plans](../protocols/dev-plan.md) and [graphs](../protocols/graph.md), while the adapter declares the concrete linter/output encoding.
- **PHASE-404** MUST: Separate a parseable plan from a semantically ready plan. Resolve ordinary deficiencies in scope with recorded deviations and required annotations; mark specBlocked only for a deficiency requiring human input, such as an unresolved numeric contradiction or unverifiable required external identifier. Preserve the deficiency list and reason; do not silently rewrite the approved specification.
- **PHASE-405** MUST: On a validated Architect SUCCESS with a ready plan and satisfied visual predicate, proceed to Code. If the specification is human-blocked or the visual predicate fails, do not enter Code; map the phase refusal to SPEC_BLOCKED or VISUAL_GATE_FAIL respectively under GATE-1203, with evidence and the decision needed. Unavailable evidence maps to BLOCKED.

## Code

- **PHASE-501** MUST: Implement the complete assigned functional slice together with its tests under the approved plan and target rules. Retain the input/output interfaces to the [coder](../roles/coder.md), [semantic markup](../code/exoskeleton.md), [logging](../code/ldd.md), [tests](../code/tests.md), [navigation](../code/navigation.md), [Doxygen](../code/doxygen.md), applicable [UI](../code/ax-ui.md) and [data](../code/data.md) protocols; their detailed authoring procedures remain at those homes. Do not replace required behavior with unfinished placeholders. For an explicitly interactive migration ticket, preserve the ordered procedure: autogenerate the migration, obtain owner review of the generated and hand-placed changes, run the sandbox validation script, then perform deliberate development apply under the recorded owner decision and authorization. The producer delivers the migration and validation evidence and the owner consumes the review/apply decisions; the human step cannot be supplied by a model verdict. Detailed migration lifecycle and validation procedures remain at [lifecycle](../process/lifecycle.md) and [tests](../code/tests.md). These migration-specific conditions do not create general autonomous gates.
- **PHASE-502** MUST: Before Code SUCCESS, verify required external APIs/dependency identifiers against actual tools or primary documentation, measure quantitative criteria, run appropriate real tests, and produce actual artifact paths, test-guide mapping, test summaries, logs/map evidence and deviations. A declared TEST_DEFERRED carries reason, infrastructure prerequisite, exact command and criterion mapping and satisfies no covered acceptance criterion. As the final Code check before SUCCESS, run mandatory applicable Doxygen and verify the current successful build exit, output and per-file XML for the authored candidate. For a product with authored code this is mandatory unless its own written instructions explicitly prohibit it; missing required configuration is a Code prerequisite still owed, not a waiver. Determine other applicability from actual configuration and declared deliverables, record any lawful nonapplicability/prohibition with evidence, and keep generated output ignored. The Code build is separate from the Finalize rebuild in FINAL-202; exact build details remain at [Doxygen](../code/doxygen.md).
- **PHASE-503** MUST: On a validated Code SUCCESS, proceed to independent QA. On a Code BUG_REPORT containing an actionable defect, stamp its fresh origin and evidence and enter the same counted Debug route used for QA defects, including before the first QA. An unavailable required environment or authorization produces BLOCKED, preserving artifacts and limitations.
- **PHASE-504** MUST: Compare any detected UI or classification discrepancy with the approved plan. Obtain the applicable classification/scope decision before acting on added UI scope; record the actual discrepancy and affected slices. A runtime limited to one slice declares that limit and refuses unsupported multi-slice routing rather than silently generalizing.

## QA and Review

- **PHASE-601** MUST: Independent QA judges a stable current candidate read-only against the specification, plan, complete acceptance map, actual test guide, logs and artifacts. Preserve independent role identity and inspect all changes including untracked bytes; no implementation writer may certify their own work as independent QA.
- **PHASE-602** MUST: Run every applicable preflight and runtime check in [the eight named scan registry](../checks/qa-scans.md), the full relevant suite and quantitative measurements, and verify required real-path, real-shape, side-effect delivery and infrastructural evidence. Account for all eight scans with actual status, reason and evidence. Green tests alone, a scan count or an example verdict cannot establish SUCCESS.
- **PHASE-603** MUST: On a validated QA SUCCESS satisfying all required scans and acceptance criteria for the current candidate, proceed to Review. On an actionable QA BUG_REPORT, stamp its fresh origin and enter counted Debug; on QA BLOCKED, stop for the owner with the required evidence and limitations. A failed or blocked required scan cannot accompany QA SUCCESS.
- **PHASE-604** MUST: Review independently examines the full current candidate diff, original requirements, correctness, regression boundaries, actual side effects and residual risks before accepted completion. On a validated Review SUCCESS for the same candidate, proceed to Finalize; actionable review defects discovered before finalization enter counted Debug and unavailable required judgment produces BLOCKED. Review evidence may be embedded in QA only when its independent producer, complete scope and timing are explicit.
- **PHASE-605** MUST: After every fix that changes the candidate implementation, renew full independent QA before Finalize, including a scoped UI fix. Renew Review when its judged evidence changed. A prior-green flag, a scoped recheck, a debugger file list or supplemental E2E MUST NOT replace the required renewed QA.
- **PHASE-606** MUST: Allow initial QA and renewed QA after the last permitted Debug entry without charging an additional repair. Assess UI and E2E applicability from the current plan; a flaky supplemental E2E cannot silently satisfy a required acceptance criterion or waive full QA.

## Debug

- **PHASE-701** MUST: Check permission and cumulative remaining Debug allowance before dispatch. Persist the spend before entering Debug as required by [run-state repairs](run-state.md); include the attempt number, cap, current origin, current failure report and the full chronological root-cause/files history in the assignment.
- **PHASE-702** MUST: Debug diagnoses from actual logs, data, code and failure evidence, records competing hypotheses where needed and fixes the root cause within authorized scope. Retain its [diagnostic role interface](../roles/debugger.md): current goal/result, cause, specific fix, files touched, scope audit, regression risk and real post-fix tests. When a check fails, rerun only its failures with detailed project trace and perform the Diagnostic Trio through the [test protocol interface](../code/tests.md); retain actual failure analysis and regression evidence. Preserve test-guide and markup/logging evidence for authored repairs; do not broaden the specification or repair unrelated work.
- **PHASE-703** MUST: On a validated Debug FIXED, proceed to renewed full independent QA. A Debug BLOCKED or failed execution preserves the consumed entry and all evidence and stops for the owner; no missing response, worker death or recovery refund disguises that spend.
- **PHASE-704** MUST: At exhausted Debug allowance, stop before another entry and escalate the still-red evidence, attempted fixes, chronological causes/files, current diagnosis, spent resources and decomposition/design concerns. Additional Debug requires an explicit bounded owner grant recorded before dispatch; the grant preserves history and the final permitted fix may still be judged by QA.

## Equivalent extensions

- **PHASE-801** MAY: An adapter declares embedded Bootstrap, reproduction/root-cause substages, supplemental recheck/E2E and typed error gates through {{cap:workflow-orchestration}}. Each declaration names producer and consumer, activation, required inputs/outputs/evidence, permissions, independence, counters and failure route; equivalence is a boundary obligation, not a claim established by a node name.
- **PHASE-802** MUST: An extension preserves approved gates, all shared phase evidence and scope restrictions, independent QA/Review, cumulative budgets and the full renewed QA predicate. Debug entered from reproduction, recheck, E2E or any error extension uses the same entry unit and spend-before-entry rule.
- **PHASE-803** MUST: A supplemental recheck reports actual passed/failed evidence and summary. A red recheck stamps the current recheck origin and diagnostic evidence and routes an actionable defect to counted Debug; a green recheck supplements and never replaces renewed QA. Label older Code/QA reports as historical context beside the fresh recheck cause.
- **PHASE-804** MUST: E2E reports passed, failed or flaky, totals, report path, traces and warnings from actual execution. A failed actionable result stamps E2E origin and routes to counted Debug; an unavailable required run blocks. A flaky result retains its evidence and warnings in final reporting; if E2E satisfies a required acceptance criterion, flaky cannot count as passed and its unsatisfied outcome must be routed explicitly. When E2E is genuinely supplemental and no required criterion depends on its pass, flaky remains a warning and does not create an actionable defect by itself.
- **PHASE-805** MUST: Optional intake/reproduction/root-cause work receives the original symptom/logs and authorized scope and returns the typed [extension interface](../protocols/role-returns.md). Nonreproduction disables automatic fix approval; proposed scope outside authorization requires the owner. A supplemental error node consumes each error once and cannot bypass the shared terminal or unknown-side-effect guard.

## Routes and terminal outcomes

- **PHASE-901** MUST: Select exactly one route from the validated phase, status, current inputs and evidence. The ordinary success route is Bootstrap SUCCESS to Architect, Architect SUCCESS to Code, Code SUCCESS to QA, QA SUCCESS to Review, Review SUCCESS to Finalize, and Finalize SUCCESS to overall SUCCESS; Debug FIXED returns to QA. These routes depend on each phase predicate above, not status text alone.
- **PHASE-902** MUST: Classify failures before routing: actionable implementation defects from Code, QA, Review or a declared implementation extension after validated plan/scope use BUG_REPORT and counted Debug within allowance; Bootstrap/Architect defects refuse continuation and require their declared blocked/error or owner route, never pre-design Debug; Finalize repair requirements use FINAL-401 and terminal failures cannot enter Debug automatically; missing permissions/environment use BLOCKED; missing/malformed responses use the bounded response-correction route; transient transport faults use their declared retry route; fatal errors abort or escalate. Preserve phase, typed kind, session identity, retryability, redacted context and last error. A failure crosses its error gate exactly once.
- **PHASE-903** MUST: Declare finite retry units and limits and apply [separate retry accounting](run-state.md). Retrying a node is permitted only when its outcome and side effects are known safe to replay. Investigate an unknown side-effect outcome before replay; an uncertain transport timeout is not evidence that nothing happened.
- **PHASE-904** MUST: Reject missing or malformed responses before state advancement. Permit at most one response-level correction for a phase attempt; a second missing/malformed response yields BLOCKED, or ESCALATED_FINALIZE during Finalize. Declared lower-level extraction/schema and transport retries remain separately bounded; exhausting them preserves their errors/cost and invokes the typed terminal handler.
- **PHASE-905** MUST: Use the canonical run-terminal vocabulary SUCCESS, SPEC_BLOCKED, VISUAL_GATE_FAIL, ESCALATED, BLOCKED, ERROR and ESCALATED_FINALIZE under GATE-1203. Every non-success terminal outcome stops the run, preserves artifacts/history and identifies the required owner decision. An adapter maps a runtime abort alias to the applicable canonical ERROR or BLOCKED outcome. Reject invalid owner payloads through a declared bounded fresh re-ask route without inventing approval; exhaustion blocks, abort terminates and an explicit grant must match the failed scope and resource need within GATE-1209 ranges.
- **PHASE-907** MUST: Every operational worker or deterministic-runner failure supplies the current node phase and typed error to its declared handler. Preserve an unexpected process crash as observable crash evidence for safe interrupted-run recovery rather than fabricating a role verdict. The adapter declares its taxonomy and handler registration as one versioned surface; adding an error kind or handler requires an explicit contract update.
- **PHASE-906** MUST: Overall SUCCESS is produced only after verified Finalize SUCCESS. A non-null result, report path, earlier QA success or exhausted loop never shortcuts Finalize; overall SUCCESS still leaves the concrete result decision required by [gates](../process/gates.md) and does not authorize integration.
