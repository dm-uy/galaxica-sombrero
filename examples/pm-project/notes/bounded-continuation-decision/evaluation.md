## Strongest contrary case

**The strongest case against recommending A is B’s separation of useful Codex delivery from the shared-neutral dependency.** The owner explicitly delegated sibling executable work to other agents. A couples main delivery to work outside this task, whereas B can preserve neutral4.0 and ordinary sibling operation during its first stage.

B’s ordinary and continuation paths need not become independent wallets: its proposal explicitly puts all continuation authority in one envelope. If a concrete caller inventory and plan demonstrate complete envelope routing with a small, well-contained refusal surface, my extra risk/maintenance penalty could be too pessimistic. Conversely, A’s schema3 migration could produce more regression work than its uniformity saves.

I retain A’s narrow recommendation because the present source strongly protects complete bindings and a single operational state path, while B’s ordinary-path/enrollment boundary is not yet demonstrated. This preference is revisable; the0.20 utility margin is not robust empirical separation.

A should be reconsidered if an authorized concrete plan shows that its new operational schema requires unrelated workflow redesign, or that B’s complete caller proof is materially smaller while preserving all accounting/refusal invariants. No new proposal round is necessary merely because B remains credible.

## Specification-level viability conditions

These belong in the proposed specification and acceptance obligations. They cannot all be deferred to local Architect judgment.

1. **Admitted historical bridge.** Name the supported3.2/schema2 parent-accounting shape and current terminal population; define causal identity, overlap reconciliation, required provenance and refusal for missing/conflicting data. Preserve aggregate4 and native0 as distinct interpretations. Hash identity does not authenticate all historic spend.

2. **Authority domain and enrollment.** Fix one authoritative lineage/storage domain and single writer, including first enrollment and subsequent successor creation. Define how supported ordinary initialization, continuation requests and dispatch callers recognize an enrolled causal chain. An operation cannot choose another lineage identifier to conceal that same admitted chain. Copies and independent hosts remain outside the guarantee.

3. **Frozen predecessors.** Preserve original native and parent bytes on all supported success/refusal paths. Explicitly cover ordinary CLI diagnostics addressing enrolled predecessors. Do not claim that an untouched old executable is prevented from editing its own files.

4. **Entry/accounting matrix.** Specify supported terminal/phase combinations and evidence predicates. Keep no-repair verification, repairs within remaining allowance, and additional-grant repairs distinct. New Code repairing the inherited cause receives the same pre-dispatch causal charge as Debug. Eligible QA remains possible at exhaustion.

5. **Reservation/recovery contract.** Commit charge, grant consumption, entry identity and dispatch reservation together before release; revalidate/read back before dispatch. A missing release stamp is not proof of nonrelease. Preserve charges and block unknown completion until actual investigation. Define safe snapshot/enrollment interruption behavior and corrupt/rollback authority refusal.

6. **Scoped retry histories.** Preserve episode identities, caps, spent turns and available costs. Define legitimate new phase/session episodes without resetting an exhausted unfinished episode. Do not add unsupported extraction/transport retries.

7. **Current evidence.** Bind current spec/plan/package/scope/candidate separately from history. Renew full independent QA after candidate-changing repair, affected Review and current Finalize. Imported accepted fields cannot supply current success.

8. **Compatibility authorization.** Name the exact Codex AST/schema/package exceptions and retain meaningful unrelated drift controls. Keep persistent schema and canonical role-return wire distinct. Version classifications must follow the actual final contract.

For **A**, schema3 and the native major boundary are explicit candidate choices. The specification must ensure “one operational contract” applies to supported new operations rather than quietly retaining a competing dispatch authority. Historical snapshots remain evidence, never independent allowances.

For **B**, additive package4.1 is conditional: compatibility means supported ordinary fresh/nonterminal API behavior under that package, not transparent rebinding of old active ledgers. Any incompatible API replacement discovered during specification must be classified before approval. Without complete caller/enrollment coverage, B is held.

Exact command spelling, internal function decomposition, serialization field names, error wording and storage mechanics within these fixed invariants are Architect details. The supported population, authority selection, proof boundaries and release conditions are specification decisions.
